# K01 HOW_TO — 의미를 보존하는 첫 WorkloadSpec

**상태: 첫 유한 task 계약과 로컬 검증 실험 완료.** 범용 작업 동등성, 분산 결과 확정, 이기종 장비 실행은 미완료다. [WHAT_IS 연구](K01_WORKLOAD_SEMANTICS.md)의 근거를 OMC에 적용한 SECONDARY_AI 설계이며, 원래의 [지식 계획](../POST_CLIENT_SERVER_KNOWLEDGE_PLAN.md)을 대체하거나 12개 과제 전체를 완료 처리하지 않는다.

## 바꾸어도 되는 것과 유지할 것

```mermaid
flowchart LR
    S[작업 ID·계약 판본·불변 입력] --> V[등록된 프로그램 변형 선택]
    V --> A[실행 시도별 계산]
    A --> C[출처·입력·결과 계약 검사]
    C --> R[검증된 결과 후보]
    R -. 후속 K03·K06 .-> P[단일 결과 확정·공개]
```

장비·파일 위치·variant·분할 크기·attempt는 실행 기록으로 분리한다. WorkloadSpec은 요청 ID, 계약 UID·revision·정의 digest, 모델·효과, 입력 encoding·digest·개수를 가진다. 바뀐 입력은 같은 Spec으로 실행할 수 없다. 같은 입력을 가진 별개의 사용자 요청도 서로 다른 workload ID를 유지한다. 입력 순서를 바꿔 합계가 같아도 입력 바이트와 요청의 정체성을 자동으로 합치지 않는다.

이번 Spec은 논리·물리 식별 분리의 작은 예제이며 K02 전체의 이름 해석·USL locator·다중 소유자 이름 공간은 아직 구현하지 않았다. 기존 HSWM 그래프나 placement CLI는 변경하지 않았다.

## 첫 계약: sum-i64-exact revision 1

정본은 [contract.json](../../research/k01_workload_contract/contract.json), 검사와 두 변형은 [workload.py](../../research/k01_workload_contract/workload.py)다.

| 항목 | 계약 |
|---|---|
| 모델·효과 | 유한 TASK / PURE. 외부 파일·서비스·보상 상태 변경 없음 |
| 입력 도메인 | signed int64 정수 0..65,536개. bool·float·문자열 거절 |
| wire encoding | 8-byte header `4f4d434936340001`, uint32 little-endian 개수, signed int64 little-endian 원소. 후행·부족 바이트 거절 |
| 계산 의미 | 수학적 정수의 정확한 합. 중간 합의 wrap·포화·조기 범위 오류 금지 |
| 성공 결과 | 합을 canonical 십진 문자열로, 개수를 작은 정수로 기록. 빈 입력의 합은 `0` |
| 도메인 오류 | 최종 정확한 합이 signed int64 범위를 벗어나면 `SUM_OUT_OF_I64_RANGE` |
| 변형 | 직접 순회하는 scalar와 청크 합을 합치는 chunked. 둘 다 이번 Python 런타임에서 실행 |
| 재시도 | 순수 계산은 다시 수행 가능. 시도 ID는 별도. 결과 공개·정산의 중복 방지는 후속 계약 |
| 취소 | verifier가 취소를 알고 있으면 후보를 거절. 실행 프로세스 중단·영속 취소 상태를 보장하지 않음 |

전체 입력 한도에서 정확한 중간 합에는 signed 80-bit 범위가 충분하다. `65,536 × 2^63 = 2^79`이고 최소값은 `-2^79`다. 따라서 네이티브 변형을 만들 때 충분히 넓은 정수 표현으로 이 계약을 구현할 수 있다. 이번에는 Python 정수로 구현했으며 C/C++의 overflow 동작이나 컴파일러 최적화를 시험한 것은 아니다.

JSON의 큰 숫자를 모든 수신자가 동일하게 해석한다고 가정하지 않도록 입력은 명시적 바이너리 형식, 큰 출력은 십진 문자열로 정했다. 이는 이 계약의 자체 wire 형식이고 보편 표준이나 RFC 8785 준수를 주장하지 않는다. 일반 HSWM 데이터 전체를 이 형식으로 바꾸는 계획도 아니다.

## 두 변형이 이 계약을 만족하는 이유

scalar 루프의 `k`번째 단계에서 누적값이 처음 `k`개 원소의 정확한 합이라는 불변식을 둔다. 초기값 0과 매 단계 정확한 정수 덧셈으로 유지되며, 유한 입력을 모두 처리한 뒤 최종 합을 얻는다. chunked는 입력을 빠짐·겹침 없이 분할하고, 각 청크를 같은 정확한 합으로 계산한 뒤 합친다. 정수 덧셈의 결합 법칙으로 같은 최종값을 얻는다. 범위 검사는 마지막 한 번으로 동일하다.

이것은 **기재한 알고리즘과 정확한 정수 연산·정상 실행을 가정한 수학적 논증**이다. Python 인터프리터, 하드웨어 또는 원격 실행자를 기계 검증한 증명은 아니다. 테스트 통과와 논증의 가정은 각각 기록한다. 전원 장애·메모리 오류·OOM·취소는 종료 보장과 별도인 실행 실패다.

## 검증기는 무엇을 확인하는가

`verify_result`는 계약/입력/요청 ID, 등록된 변형과 코드 digest, 시도 메타데이터, 결과 바이트 hash, 실제 결과 조건을 확인한다. oracle은 입력을 값별 등장 횟수로 묶어 정확한 합을 별도로 계산한다. 같은 Python 정수 런타임을 쓰므로 그 런타임의 공통 결함까지 독립적으로 검출한다고 주장하지 않는다.

반환값 True는 **이 로컬 검사에서 올바른 결과 후보라는 뜻**이다. 한 결과만 최종 확정했다는 뜻도, 제출자가 실제로 해당 프로그램을 실행했다는 인증도 아니다. 후보의 artifact hash는 이 연구의 신뢰된 로컬 registry와 대조하는 정보이며 서명·원격 attestation은 없다. 두 변형은 같은 Python 소스 파일 안에 있어 artifact digest는 같고 variant ID가 다르다. 개별 네이티브 바이너리는 후속 연구에서 각각 등록한다.

소스 수정 뒤 과거 결과 기록의 digest가 달라지면 과거 원문과 실험을 그대로 보존하고 새 실험 판본을 만든다. 계약 정의 파일을 조용히 바꾸는 것도 코드에 고정한 definition digest가 거절한다.

## 실제 실행 결과와 재현

[experiment.json](../../records/2026-10-11/k01-workload-contract/experiment.json)에 환경·seed·코드/입력 집합 digest와 결과를 남겼다.

- 입력 **4,115개**: `{-2,-1,0,1,2}` 길이 0..5의 모든 3,906개, 경계 9개, seed `20261011`의 임의 입력 200개.
- 입력마다 scalar 1개와 chunk size 1·2·7·64의 chunked 4개: **20,575개 후보 검증 통과**.
- 경계/임의 입력의 역순 실행 **209개**에서 같은 결과 조건 확인. 입력·요청 식별은 별도로 유지.
- 고의로 잘못 만든 변형 **5종 모두 거절**. 잘못된 결과 자체의 hash가 일치해도 거절.
- 입력·Spec·출력·출처·취소 반례를 다룬 **단위 검사 14개 통과**.
- 응답 유실/중복 효과는 별도의 작은 상태 모형으로 관찰. 실제 네트워크 장애 시험은 아님.

```sh
python3 -m unittest discover -s research/k01_workload_contract -p 'test_*.py' -v
python3 research/k01_workload_contract/run_study.py --output .local/k01-reproduction.json
python3 records/2026-10-11/k01-workload-contract/validate.py
```

실험 명령은 기존 결과 파일을 덮어쓰지 않는다. 재실행에는 새 output 경로를 쓴다. 유한 표본의 성공은 전체 signed int64 입력 공간의 전수 검증이 아니다. 한 장비의 로컬 정확성 연구이며 배치 최적화·속도 향상·다른 ISA·실제 병렬 실행은 측정하지 않았다.
