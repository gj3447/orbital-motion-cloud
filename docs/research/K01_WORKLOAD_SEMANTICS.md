# K01 WHAT_IS — 작업의 동일성·재시도·효과는 무엇이 다른가

첫 연구 질문은 **프로그램과 장비가 달라도 같은 작업을 수행했다고 무엇을 근거로 말할 수 있는가?**다. [12개 지식 과제](../POST_CLIENT_SERVER_KNOWLEDGE_PLAN.md)의 K01을 다룬다. 사용자 요청은 [원문](../../records/2026-10-11/k01-workload-contract/user-verbatim.txt), 아래 분석은 SECONDARY_AI다. CHU의 전체 인지 작용을 정수 계산으로 정의하지 않는다.

## 동일성의 대상부터 정한다

같은 바이너리는 같은 입력·환경·상태를 보장하지 않는다. 반대로 서로 다른 바이너리가 같은 결과 계약을 만족할 수 있다. 이 연구에서는 바이트 동일성, 한 입력에서의 결과 일치, 허용된 모든 입력에 대한 계약 만족, 외부 효과의 동등성을 구별한다.

OMC의 첫 계약은 `입력 조건 P + 허용된 효과 E + 결과 조건 Q`로 기술한다. 후보 variant는 해당 조건 아래에서 같은 관찰 가능한 결과를 내야 한다. 시간·전력·RAM 사용은 계약에 명시한 자원 한도의 범위에서 달라질 수 있다. 출력 수치만 같아도 권한 없는 파일 변경을 했다면 전체 계약을 만족했다고 볼 수 없다. 이번 로컬 코드 검사는 원격 코드의 부작용을 탐지하는 샌드박스가 아니다.

`항상 종료하는가`, `응답이 왔는가`, `올바른 결과인가`, `외부 효과가 확정됐는가`도 서로 다른 질문이다. 타임아웃은 관측된 시간 안에 완료 응답을 받지 못했다는 상태로 남겨야 한다. 그 사실만으로 작업이 실행되지 않았거나 잘못된 결과를 냈다고 판정하지 않는다.

## 실행 단위별 필요한 계약

아래는 OMC 설계에 적용하기 위한 분류다. 특정 프레임워크와 CHU의 정체성을 합치는 주장이 아니다.

| 단위 | 의미를 보존하려면 필요한 정보 | 초기 적용 |
|---|---|---|
| 유한 task | 불변 입력 판본, 결과 판정법, 종료/취소 조건, 허용 효과 | 외부 쓰기가 없는 정수 집계로 구현 |
| 상태를 가진 actor/service | 상태 판본·현재 소유자, 메시지 순서, 상태 전이, snapshot/복구 조건 | 설계 요구만 기록; 이전·복구 미구현 |
| stream | 사건 ID, 순서·중복·누락 기준, window 종료, offset/checkpoint, backpressure | 설계 요구만 기록; 실행 미구현 |

상태를 가진 인지 작업을 이름만 task로 바꾸면 상태 이전 문제가 사라지지 않는다. 난수·시각·외부 조회가 결과에 필요하면 입력으로 고정하거나 비결정성을 결과 판정 계약에 명시해야 한다. LLM 출력의 문장 일치와 지식의 타당성은 별도 문제이며, 이번 정확한 정수 oracle을 그대로 적용할 수 없다.

## 재시도와 중복 효과

외부 변경을 수행한 뒤 응답이 유실되면 호출자는 성공 여부를 모를 수 있다. 그 상태에서 같은 요청을 다시 보내면 효과가 두 번 생길 수 있다. 반대로 재시도를 막으면 실행되지 않았던 요청이 영원히 빠질 수 있다. 결과 ID나 멱등 키를 붙이는 것만으로 수신자의 처리 계약이 완성되지는 않는다.

이번 [상태 모형](../../records/2026-10-11/k01-workload-contract/experiment.json)은 응답 유실 후 재시도에서 효과 횟수가 2가 되는 경로와, **효과 변경과 operation key 기록을 하나의 원자 전이로 처리한다는 가정** 아래 1이 되는 경로를 비교했다. 이것은 시뮬레이션이며 실제 DB·네트워크 장애 실험은 아니다. 그 가정을 구현하려면 K03·K06의 동시성·내구 실행 연구가 필요하다.

따라서 첫 계산 task의 반복 실행을 허용하더라도 결과 공개·보상 지급까지 반복 허용으로 전파하지 않는다. 취소 요청도 이미 발생한 효과를 자동으로 되돌리지 않는다.

## 직접 확인한 수치 반례

[로컬 실험](../../records/2026-10-11/k01-workload-contract/experiment.json)은 다음 다섯 잘못된 결과를 모두 거절했다. 입력과 결과는 십진 문자열로 기록해 큰 정수의 JSON 소비 과정에서 정보가 손실되지 않게 했다.

| 잘못된 변형 | 반례 | 계약상 필요한 결과 |
|---|---|---|
| 정수를 float으로 변환해 합산 | `9007199254740992 + 1` | 정확히 `9007199254740993` |
| signed int64 wrapping | `9223372036854775807 + 1` | 최종 합이 범위를 벗어났다는 명시적 DOMAIN_ERROR |
| 최대값으로 포화 | 같은 입력 | 최대값으로 잘라 성공시키면 안 됨 |
| 중간 합 overflow 즉시 실패 | `[9223372036854775807, 1, -1]` | 최종 합 `9223372036854775807`로 성공 |
| 입력 하나 누락 | `[1, 2, 3]` | 개수 3, 합 6 |

잘못된 결과의 SHA-256을 다시 계산해 붙여도 의미 검사가 거절했다. **해시 일치는 바이트 확인이며 작업 정확성 검증과 다르다.** 외부 프로그램의 서명·실행 증명이나 무신뢰 검증을 구현한 것은 아니다.

## 이번 연구가 확보한 것

작업의 의미를 입력·출력뿐 아니라 효과·재시도·취소·오류까지 묶어 정의해야 한다는 설계 근거, 정확한 집계의 분할 조건, 그리고 이를 깨뜨리는 실제 반례를 확보했다. 다음 [HOW_TO](K01_WORKLOAD_CONTRACT.md)는 그 결과를 첫 WorkloadSpec과 실행 가능한 작은 검사기로 옮긴다.
