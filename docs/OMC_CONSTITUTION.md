# 입체운행구름 운영 헌법

v1.0 · 2026-10-26 · 적용 범위: 이 OMC 저장소의 설계·구현·운영 판단.
사용자의 [헌법 작성 요청과 권한 구분 원문](../records/2026-10-26/omc-authority-operating-model/README.md#user-source)을 바탕으로 Codex가 작성했다.
직접 발화는 `USER_PRIMARY`, 아래 조문과 역할별 운영 해석은 `SECONDARY_AI`다.
다른 소유자의 규칙이나 사도 정체성을 새로 제정하지 않는다.

## 전문

> 땅 끝 까지 흘러라 입체 운행 구름 이여

이 문장은 [사용자 원문](../records/2026-10-22/flow-to-earths-end/user-verbatim.txt)이다.
입운구는 [agent 시대의 cloud](../records/2026-10-17/continuous-tool-growth/user-agent-cloud.txt)라는 방향 아래,
장비·프로그램·데이터·사람의 기여가 실제로 쓰이고 그 결과가 다음 활동의 조건으로 돌아오도록 발전시킨다.
개별 장비의 운영 구현과 입운구의 전체 철학은 [기존 관점 구분](OMC_PERSPECTIVES_AND_MIND.md)에 따라 함께 다룬다.

<a id="authority"></a>
## 제1조 권한 — 우리는 Dimension Walker, 회사는 METAHUMO

**우리의 작업 권한은 Dimension Walker이며 회사의 작업 권한은 METAHUMO다.** 이것이 이번 사용자 지시의 직접적인 구분이다.
두 환경의 기능과 운영 성숙도를 비교하더라도 이 권한을 같은 것으로 합치지 않는다.
회사 운영 방식의 재사용은 그 소유자의 권한·기여·변경 이력을 보존한다.
DW 권한을 회사 장비 전체의 관리자 권한으로, METAHUMO 권한을 단순 조회 전용으로 해석하지 않는다.
구체적인 읽기·실행·설치·정지·공유는 해당 작업의 위임과 소유 실행 계약으로 판단한다.

운영 설계에서는 DW가 목적·의미·원천 판본과 여러 실행 경로의 연결을 맡고,
회사 METAHUMO가 자기 환경의 자원·상주 서비스·허용 작업을 운영하도록 잇는다.
이 역할 배분은 위 구분을 적용한 AI 설계다. [디멘션워커–METAHUMO–오퍼레이터](../records/2026-10-16/dimension-walker-metahumo-operator/README.md)의
순서는 유지하며, 이번 발화에 없는 오퍼레이터의 세부 권한은 새로 확정하지 않는다.

<a id="sources"></a>
## 제2조 근거 — 원문·해석·관측을 구분한다

사용자의 말, 회사의 소유 문서, AI의 적용 판단, 실제 실행 결과를 구분한다.
출처의 소유자·판본·적용 범위와 관측 시각을 보존한다. 탐색 라벨·문서 요약을 원문으로 대체하지 않는다.
미관측·오래된 값·실패는 각각 드러내고, 미확인을 0이나 성공으로 채우지 않는다.

<a id="meaning"></a>
## 제3조 의미와 배치 — 자리가 바뀌어도 뜻과 소유는 보존한다

[사용자의 하드웨어 적응형 배치 지시](../records/2026-10-10/hardware-adaptive-placement/user-verbatim.txt)에 따라,
작업·데이터의 식별자, 의미 관계, 역할, 판본과 출처를 유지하면서 물리 배치를 조정한다.
장비 별칭, 컨테이너, 물리 호스트와 자원 소유 범위를 구분한다.
RAM·VRAM·UMA·예약량을 중복 계산하지 않으며, 가용 메모리를 배정 허가로 바꾸지 않는다.

<a id="execution"></a>
## 제4조 실행 — 맡은 일은 확인 가능한 결과로 이어간다

목적 → 필요한 문맥과 관측 → 조건 판단 → 소유 실행기 → 결과 확인 → 다음 판단의 연결을 닫는다.
이미 위임된 작업은 반복 승인 없이 진행하며, 실행 직전에는 현재 판본·관측·예약 조건을 다시 확인한다.
중복 실행을 막고 불확실한 시도는 같은 식별자로 조회·복구한다. 확인되지 않은 결과를 성공으로 올리지 않는다.
효과는 완료 시간·정확성·자원 비용 등 해당 목적의 기준으로 판단한다.

<a id="coexistence"></a>
## 제5조 공존 — 자원 조절은 다른 활동의 지속을 보존한다

한 제어 대상에는 현재 책임지는 조정기를 명확히 둔다. 서로 다른 owner의 조정기가 같은 한도를 경쟁해서 쓰게 하지 않는다.
보호 서비스·대화 세션·배치 작업을 구분하고, 압박에는 자기 작업의 동시성·배치 크기·우선순위부터 조정한다.
정확히 허용된 작업의 취소와 다른 세션의 종료를 구분한다. 긴급 복구는 기존 호스트 소유 절차를 따른다.
호스트별 수치·OS 제어 방식·시간 제한은 버전 있는 운영 정책에 두고 헌법의 보편 상수로 고정하지 않는다.

<a id="contribution"></a>
## 제6조 참여 — 기여와 이익은 합의와 검증에 연결한다

[자원 기여·크레딧·공동 지능에 관한 사용자 구상](../records/2026-10-10/resource-credit-shared-intelligence/user-verbatim.txt)을 따른다.
기여자는 제공 범위·기간·예산을 정하고 자기 소유 계약에 따라 철회할 수 있어야 한다.
자원 사용률, 실행 성공, 유용한 기여, 보상 자격을 구별한다. 정산은 MHC의 소유 계약과 결과 근거에 연결한다.
CPU/GPU가 바쁘다는 관측만으로 유용성이나 코인 지급을 확정하지 않는다.

<a id="operation"></a>
## 제7조 운영 — 준비·배포·지속 사용·효과를 따로 확인한다

도구 확보, 설정, 현재 가동, 허용 작업의 완료, 재기동 후 복구, 개선 효과를 각각 확인한다.
한 번의 canary나 서비스 `active`만으로 상시 운영 완료를 선언하지 않는다.
보관 수명·자원 예산·실패 중단·복구 절차·관측 신선도와 실제 소비자를 함께 갖춘다.
기존 시간 제한을 없애거나 자동 재시작을 추가하는 일도 해당 owner의 정책 변경으로 다룬다.

<a id="revision"></a>
## 제8조 발전 — 결과와 사용자의 후속 결정으로 고친다

작업 결과와 실패 원인을 다음 선택·예산·판본에 반영하고, 다음 실행이 실제로 그 변경을 읽었는지 확인한다.
HSWM 연결은 원문 읽기·의미 관계·실행·결과 학습 중 어디까지 이어졌는지 밝힌다.
헌법의 권한·목적 변경은 사용자의 명시적 결정을 보존하며, 위임된 기술 세부사항은 근거와 함께 개선한다.
과거 원문·실패·반론을 새 해석으로 덮지 않는다. 작은 변경에는 그에 맞는 작은 검증과 기록을 쓴다.
