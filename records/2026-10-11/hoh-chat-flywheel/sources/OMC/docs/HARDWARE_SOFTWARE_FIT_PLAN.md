# 하드웨어에 맞춰 실현되는 OMC 구축 계획

OMC의 목표는 서로 다른 컴퓨터·데이터·프로그램을 하나의 협력 구조로 묶되, 각 장비의 실제 특성에 맞는 실행 형태를 선택하는 것이다. **공통으로 유지할 것은 의미·연결·결과 계약이고, 하드웨어에 맞춰 달라질 것은 프로그램 변형·실행 설정·데이터 위치다.** CHU OS에서는 관측 → 제안 → 검증 → 실행 → 결과 학습의 순환으로 이 선택을 거의 자동화한다.

2026-10-10의 [사용자 원문](../records/2026-10-10/hardware-software-fit/user-verbatim.txt)과 [CHU OS 방향 발화](../records/2026-10-10/hardware-software-fit/chu-os-user-verbatim.txt)는 USER_PRIMARY로 별도 보존한다. 아래 기술적 해석과 계약은 Codex의 SECONDARY_AI 제안이다. 현재 산출물은 HOW_TO 설계이며, 범용 자동 실행기의 구현 완료를 뜻하지 않는다.

## 발화의 의미

“신일 합일”이라는 표현은 원문 그대로 둔다. 이를 기술적으로 풀면 소프트웨어가 하드웨어의 차이를 지워 버리기보다, CPU 명령어·메모리 구조·가속기·저장장치·네트워크의 성질을 실행 방식에 반영한다는 뜻으로 이해할 수 있다. 추상적인 기능이 실제 기계 위에서 어떤 형태로 구현되는지까지 OMC가 다룬다.

예를 들어 같은 데이터 처리 계약을 CPU 중심 장비에서는 벡터 명령어와 여러 스레드로, 지원되는 가속기 장비에서는 해당 백엔드로 수행할 수 있다. 큰 원문은 저장 용량이 충분한 장비에 두고, 반복 사용하는 조각은 연산 장비 가까이에 둘 수 있다. 이것은 가능한 설계 예시이며 현재 장비의 성능이나 가속기 지원을 측정한 결과는 아니다. 서로 다른 목적의 프로그램은 별도 workload ID를 유지하고, 같은 계약을 충족한 구현들만 서로 대체 가능한 변형으로 취급한다.

이 관점에서 AI native는 단순히 실행 명령을 자연어로 생성하는 기능보다 넓다. AI가 작업 의미와 현재 자원 제약을 함께 읽어 후보를 만들고, 도구가 그 후보의 실현 가능성을 확인하며, 실제 결과가 다음 선택의 근거가 되는 구조다. 자유롭게 기여하는 장비들의 차이가 협력의 재료가 된다. 자원 제공자의 사용 한도·회수 의사·기여 기록도 배치 계약에 포함한다. 보상 코인의 가격·발행·정산은 별도 경제 계약이며 이 성능 계획으로 확정하지 않는다.

## 쿠버네티스와 비교할 지점

원문의 “공산주의처럼”은 획일적 운용을 설명하기 위한 사용자 비유로 보존한다. Kubernetes 자체가 모든 장비와 프로그램을 똑같이 만들도록 강제한다는 기술 명제로 옮기지는 않는다. Kubernetes도 노드별 조건에 따른 배치와 선호도를 제공하며, Topology Manager로 NUMA 자원 배치를 조정한다. [노드 배치 공식 문서](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/), [Topology Manager 공식 문서](https://kubernetes.io/docs/tasks/administer-cluster/topology-manager/).

따라서 OMC가 검증할 차별점은 **하드웨어를 의식하는 배치에 더해, 작업 의미를 보존하는 프로그램 변형·데이터 배치·실행 설정을 함께 선택하고 개선하는가**다. 기존 [Kubernetes·Borg 연구 보존본](../sources/SYMPOSIUM/METAHUMOTONIC/ORBITAL_MOTION_CLOUD/KUBERNETES_BORG_ABSORPTION_2026-07-15.md)의 제어 순환·필터링·충돌 감지 논의를 참고하되, 그 문서의 PRELIMINARY 해석과 당시 실행 주장을 이번 사용자 확정이나 현재 실측으로 승격하지 않는다.

## 불변인 의미와 변하는 실현

`G`는 HSWM의 논리 그래프, `H(t)`는 시각과 유효기간이 있는 하드웨어 관측, `R(t)`는 물리 실현이다. OMC는 `G`를 그대로 두고 `H(t)`와 작업 계약에 따라 `R(t)`를 선택한다. 논리적 추상화는 유지하면서 불필요한 실행 중간층은 줄일 수 있다.

| 유지할 계약 | 조절할 실현 |
| --- | --- |
| HSWM 자원 ID·의미·관계·참여 역할·출처 | 장비 선택·데이터 복사본·USL locator |
| 입력·출력 스키마와 정확성·허용 오차 | CPU ISA별 빌드·검증된 알고리즘·가속기 백엔드 |
| 데이터 내용의 식별과 revision | 캐시·청크·배치 크기·데이터를 읽는 경로 |
| 소유자의 자원 사용 한도와 취소 조건 | 스레드 수·메모리 한도·CPU 및 NUMA affinity |

프로그램 변형의 바이너리 해시는 당연히 다를 수 있다. 그 변형은 새 artifact ID와 빌드 출처를 갖고, 기존 workload 의미 계약을 만족하는지 별도 검증받는다. 바이너리 바이트의 동일성과 계산 의미의 동일성을 혼동하지 않는다. 부동소수점 오차나 비결정성이 허용되는 작업은 허용 범위를 계약에 먼저 적는다. 압축·변환한 데이터 역시 새 representation과 복원 조건을 기록한다.

현재 [데이터 배치 CLI](HARDWARE_ADAPTIVE_PLACEMENT.md)는 선택한 locator 외의 입력 그래프 전체를 보존한다. 새 실행 계획·하드웨어 관측·프로그램 변형은 별도 운영 그래프에 두고 그 논리 그래프를 참조한다. 자원 위치가 바뀌었다고 HSWM의 의미 관계를 다시 쓰지 않는다.

## 네이티브 실행 원칙

첫 구현 목표는 소유자가 허용한 물리 호스트에서 운영체제·드라이버·네이티브 라이브러리를 직접 사용하는 실행기다. 워크로드를 돌리기 위해 새 VM이나 컨테이너 계층을 필수로 만들지 않는다. 프로세스 권한·자원 상한·취소·복구는 여전히 필요하므로 OS 수준의 프로세스 관리와 하드웨어 가상화를 구별한다. 구체적인 OS 실행 adapter는 소유 저장소의 기존 실행 계약에 맞춰 정한다.

현재 Proxmox 등의 기반을 사용 중인 관측 경로에서는 물리 호스트와 게스트를 구별해 기록하고, 게스트에서 본 CPU·메모리를 곧바로 전체 물리 장비의 여유로 해석하지 않는다. 이 계획은 기존 VM 철거나 서비스 이전 명령이 아니다. 네이티브 실행의 성능 이점도 측정 대상이며 언제나 더 빠르다고 가정하지 않는다.

## 운영 그래프 계약

기존 OMC subject UID `sym:Character:입체운행구름`과 데이터 배치 capability UID를 재사용한다. 새 설계 노드는 OMC 소유 namespace 안에 둔다. CHU OS는 이번에 조회한 KG와 허브 문서에서 정확한 정본 UID를 확인하지 못했으므로, 사용자 발화가 지칭한 미래 통합 대상으로만 연결한다. 이름이 비슷한 기존 엔티티와 합치지 않는다.

| 노드 | 기록할 내용 |
| --- | --- |
| WorkloadSpec | 안정된 ID, 의미 계약 revision, 입출력, 정확성·허용 오차, 자원 한도, 취소·효과 계약 |
| HardwareProfile | 장비 ID, 물리·게스트 구분, ISA·NUMA·가속기·메모리·저장·네트워크 능력 |
| Observation | 대상 profile, 관측 시각·TTL·부팅 ID, 가용량과 부하, 측정 도구·오차·미관측 항목 |
| ProgramVariant | artifact digest, 소스·빌드 도구 판본, ABI·ISA·드라이버 조건, 충족할 workload 계약 |
| DataResource와 Replica | 논리 자원·revision·내용 해시와 실제 복사본 locator, 장치·장애 영역 |
| ExecutionPlan | workload·variant·대상 장비·관측 핀·입력 복사본, 고정 argv, 예약, 예산, 이전 세대, 취소·복구 방법 |
| Run과 Outcome | 실제 실행 ID, 사용한 계획, 실행 상태, 정확성 검사, 총 소요시간·자원 비용·실패 근거 |

`ProgramVariant → IMPLEMENTS → WorkloadSpec`, `ExecutionPlan → SELECTS_VARIANT → ProgramVariant`, `ExecutionPlan → TARGETS_HARDWARE → HardwareProfile`처럼 방향과 기수를 명시한다. 계획은 한 실행 단위와 한 장비를 대상으로 하고, 분산 작업은 여러 자식 계획으로 구성한다. 실제 실행은 계획과 별도 Run으로 기록하며, 관측 없는 성능 값을 만들지 않는다.

[설계 그래프와 계약](../graph/hardware-software-fit.proposal.json)에 현재 재사용 대상, 불변 조건, 변경 가능한 차원, 단계별 조건, 위 운영 노드·관계의 초안을 함께 둔다. UID·끝점·domain/range·기수·출처 바이트·단계 의존성·여섯 질의의 정확한 답을 [검사기](../records/2026-10-10/hardware-software-fit/validate.py)로 확인한다. 로컬 typed property graph 제안이며 RDF·OWL·SHACL 인증이나 공유 KG 게시를 뜻하지 않는다.

## 선택과 실행의 순환

```mermaid
flowchart LR
    W[작업 의미와 결과 계약] --> P[AI가 실행 변형과 배치 제안]
    H[장비 능력과 유효한 상태 관측] --> P
    O[이전 실행 결과] --> P
    P --> V[호환성·예약·정확성 근거 검사]
    V --> E[소유 실행기의 제한된 네이티브 실행]
    E --> C[결과와 전체 비용 검증]
    C --> O
    C --> R[유지·원복·다음 후보 선택]
```

AI의 제안과 실행 적격성 판정은 별도다. 처음에는 등록된 변형과 설정 범위 안에서만 후보를 만든다. 새 코드 생성·재컴파일은 독립 빌드와 의미 검증을 통과한 artifact가 된 뒤 후보에 들어온다. 실행 직전 관측 신선도, 가용 자원 예약, 코드·입력 digest, 기존 상태 세대를 재확인한다. 단일 자원에 대한 서로 다른 실행기의 예약 충돌을 거부하고, 원격 작업은 임대 만료와 fencing 세대로 오래된 writer의 재진입을 막는 계약이 필요하다.

비용은 `이동 + 빌드 + 대기 + 실행 + 검증 + 재배치`를 포함한다. CPU 시간·RAM·저장 공간·전력·지연을 단위 없이 더하지 않는다. 우선 정확성·용량·소유 한도 같은 필수 제약을 통과시킨 후, 선언한 지연·비용 목표로 비교한다. 정책에 따라 정규화·가중치 또는 우선순위를 명시하고 예상치와 실측치를 분리한다. 전역 최적해를 보장하는 대신 관측한 조건에서 기준선보다 나은 선택을 찾는다.

재배치에는 이득 문턱과 최소 유지 시간을 둬서 작은 부하 변화마다 작업을 옮기지 않게 한다. 상태가 있는 프로그램은 정지·체크포인트·재시작 또는 멱등성 계약이 있어야 이동시킨다. 측정 가능한 개선이 없으면 기존 배치를 유지한다. 실패한 실행의 결과를 성공한 지식이나 성능 학습 표본으로 잘못 합치지 않는다.

## 구현 순서와 종료 조건

| 단계 | 만들 것 | 다음 단계로 넘어갈 근거 |
| --- | --- | --- |
| 1 계약과 읽기 전용 관측 | 위 스키마와 소유 범위, 물리·게스트 구분, 장비별 capability 및 TTL 관측 adapter | 잘못된 ISA·오래된 관측·누락된 용량을 후보 적격으로 만들지 않음 |
| 2 실행하지 않는 비교 계획 | 고정 workload 하나, 기준 variant, 후보 variant, 데이터 이동을 포함한 비용 비교 | 같은 입력에 대해 선택 이유·제약·예상 비용을 재현하고 예상·실측을 구별함 |
| 3 제한된 네이티브 실험 | 호환성이 확인된 서로 다른 두 장비에서 같은 계약을 수행하고, 기존 데이터 배치 CLI로 확정 입력을 연결 | 출력 계약 만족, 전체 시간·메모리·전송량의 기준선 비교, 취소와 중단 복구 성공 |
| 4 제한된 자동 조정 | 소유 실행기 예약·fencing, 작은 canary, 원복, 반복 재배치 억제 | 충돌·장애·성능 악화 주입 시 원래 상태 또는 기록된 복구 상태로 수렴 |
| 5 CHU OS 연결 | workload 접수와 OMC 계획·실행·결과 인터페이스, 소유자 한도와 취소, 결과 축적 | 동일 계약을 여러 장비·작업으로 확장해도 의미·링크·출처가 보존되고 개입 빈도와 개선 폭을 측정 가능 |

첫 실험 후보는 부작용이 적고 결과를 판정할 수 있는 확정 데이터 처리 작업이다. 실제 작업과 장비는 1단계 관측으로 고른다. 실험 전에 입력 digest, 장비 상태, 반복 횟수, warm/cold 조건, 허용 오차, 중단 기준을 고정한다. 결과가 좋지 않아도 이를 보존하고 다음 후보를 고른다. 현재 20TB·4TB 배치 adapter는 파일 보존·검증·locator 변경을 재사용하는 기반이며, 아직 범용 프로그램 실행과 자동 최적화를 수행하지 않는다.

필수 반례는 미지원 ISA/ABI, 허용 오차를 넘은 결과, 바뀐 입력, 만료된 관측, 자원 이중 예약, 이동 중 장애, 실행 뒤 결과 기록 전 중단, 개선 없는 과잉 재배치다. 각 반례에서 잘못된 실행 승인이나 거짓 성공 기록이 생기지 않아야 한다. 설계 그래프 검사는 이 런타임 반례를 통과했다는 뜻이 아니다.

## 연구 연결

주된 질문은 기존 제품의 정의보다 OMC를 어떻게 발전시킬지이므로 HOW_TO다. 기존 `infrastructure-orchestration` 연구 주제와 OMC의 하드웨어 적응형 데이터 배치를 확장한다. 별도 사도·새 정본·새 일반 오케스트레이터 저장소를 만들 근거는 없다. THE GREAT FLOW의 기존 연구 워크플로에 이 계획의 고정 바이트를 누적하고, 실행 구현은 OMC와 각 소유 실행기의 계약에 따라 후속 작업으로 진행한다.
